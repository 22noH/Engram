# 코드 독 패널 — 탭 브라우저 · 자유 분할 (2026-07-25)

목업 승인: `scratchpad/dock-panel-mockup.html`(사용자 확정 — 진짜 브라우저 교체 + 자유 분할).

## 왜

지금 코드 패널은 `터미널 | 미리보기 | Diff` 셋 중 **하나만** 보이는 단일 탭 구조다. 실제 작업은 "서버 화면 보면서 터미널 치기"처럼 동시에 필요하고, 미리보기는 `iframe`이라 **뒤로/앞으로가 원천 불가**(cross-origin history 접근 차단)이며 `http(s)`만 받아 로컬 파일을 못 연다.

## 무엇을

1. **독(dock)**: 칸(pane)을 자유롭게 나눠(상하·좌우, 3칸 이상) 각 칸에 도구를 담는다.
2. **칸마다 탭**: 브라우저 칸은 여러 URL, 터미널 칸은 여러 세션, Diff 칸은 여러 파일.
3. **진짜 브라우저**: 뒤로/앞으로·새로고침·주소창·외부 열기가 전부 동작.
4. **드래그&드롭**: 파일을 끌어다 놓으면 브라우저 칸의 새 탭으로 열린다(로컬 HTML 미리보기 흡수).

## 핵심 기술 결정 — 브라우저 부품

`iframe`으로는 요구를 못 채운다(히스토리 제어 불가). Electron 선택지:

| 방식 | 히스토리 제어 | 배치 난이도 | 위험 |
|---|---|---|---|
| `<webview>` | ○ `goBack/goForward/reload` | 낮음(일반 DOM 요소처럼 배치) | Electron이 비권장(성능·버그), 그러나 여전히 동작 |
| `WebContentsView`(메인) | ○ | 높음(메인이 좌표를 직접 계산·동기화) | 렌더러 레이아웃과 어긋나기 쉬움(스크롤·리사이즈) |

**결정: `<webview>`**. 자유 분할이라 칸 위치·크기가 수시로 바뀌는데, 메인 프로세스가 좌표를 따라다니는 `WebContentsView`는 분할·리사이즈마다 어긋날 위험이 크다. `webview`는 DOM 흐름에 그대로 얹혀 레이아웃이 공짜다.

**안전 설정(필수)**
- `webpreferences="contextIsolation=yes,nodeIntegration=no,sandbox=yes"`, `allowpopups` 미지정.
- `partition="persist:engram-preview"` — 앱 세션과 **분리**(외부 사이트가 앱 쿠키/스토리지에 접근 금지).
- `will-navigate`/`new-window`를 가로채 **탭 안에서만** 이동하고, 외부 새 창 요청은 OS 브라우저로.
- `webviewTag: true`는 채팅 창 `webPreferences`에만 켠다(설정창은 그대로).

## 데이터 모델(렌더러)

```
DockLayout = { root: Node }
Node = Split { dir: 'row'|'col', children: [Node, Node], sizes: [number, number] }
     | Pane  { id, tool: 'browser'|'terminal'|'diff', tabs: Tab[], activeTabId }
Tab  = { id, title, ... }   // browser: url  / terminal: sid  / diff: file
```
- 이진 분할의 재귀 트리 = 자유 분할을 가장 단순하게 표현(3칸 이상은 중첩으로).
- 순수 함수로 분리해 테스트: `splitPane(layout, paneId, dir)`, `closePane`, `moveTab`, `resize`.
- 채널별 레이아웃을 `localStorage`에 저장(기존 `OPEN_KEY` 관례 확장). 깨진 값은 기본 레이아웃으로 폴백.

## 칸별 규칙

- **브라우저**: 주소창(입력→이동), ←/→/⟳, ↗(외부 열기). `http(s)` + **로컬 파일 경로**(파일은 읽어서 `srcdoc`이 아니라 `file://`로 로드 — webview는 iframe과 달리 로컬 파일 로드가 가능하다. 단 파티션 분리 유지). 채팅의 HTML 카드 "크게 보기"는 새 탭으로.
- **터미널**: 기존 `pty-manager` 그대로. 칸/탭이 늘면 세션도 늘어난다 — **`before-quit` killAll이 전부 정리하는지 반드시 재확인**(고아 방지, 기존 불변식).
- **Diff**: 기존 `git-diff` 그대로, 파일당 탭.

## 함정(선례 기반)

- **터미널 세션 누수**: 탭/칸을 닫으면 그 세션을 kill해야 한다. 반대로 **패널만 접을 땐 kill 금지**(기존 규칙 — 세션 유지).
- **webview 로드 실패**: 오프라인·잘못된 주소는 명확한 안내(무반응 금지). `did-fail-load` 청취.
- **리사이즈 폭주**: 드래그 중 매 픽셀 상태 갱신 금지(rAF 또는 드래그 종료 시 확정).
- **기존 회귀 0**: 코드 채널이 아니면 독 자체가 안 뜬다. 기존 단일 패널 사용자 상태(localStorage)는 기본 레이아웃으로 자연 이관.

## 브라우저 칸 부가 메뉴(목업 승인)

- **서버 메뉴**: 개발 서버 목록(이름·포트·실행중 표시) + ▶ 시작/중지 + "서버 추가". 시작하면 그 주소로 자동 이동. 실행은 기존 `pty-manager` 재사용(별도 프로세스 감독 만들지 말 것).
- **더보기(⋮)**: 파일 열기 · 스크린샷 저장 · 허용된 사이트 관리 · 채팅 링크를 이 패널에서 열기(토글) · 세션 유지(기본 "유지 안 함" = 비영속 파티션).
- ~~자동 확인 비활성화~~ → **AI 웹 조작 도입으로 의미가 생김**(아래 참조). 조작 없이 넣으면 빈 껍데기라 조작과 함께 붙인다.

# 2단계 — AI 웹 조작(자가 테스트)

목업 승인: `scratchpad/ai-browser-mockup.html`. **독 패널 완성 후 착수**(사용자 확정 순서).

## 왜
지금은 코드를 짜고 나면 사람이 열어서 확인해야 끝난다. AI가 자기가 만든 화면을 직접 열고 눌러보고 **콘솔 오류까지 읽어 스스로 고치는 순환**을 만든다.

## 도구(브레인에게 노출)
`browser_navigate` · `browser_click` · `browser_type` · `browser_read`(화면 내용) · `browser_console`(오류) · `browser_network` · `browser_screenshot`.

`<webview>`가 이걸 전부 제공한다(`executeJavaScript`, `sendInputEvent`, `capturePage`, `console-message`/`did-fail-load` 이벤트).

## ★최대 난관 — 채널 정체성 바인딩
위키 `ask-user-ui-mcp`에 기록된 선례: **MCP 도구는 "어느 채널인지"를 알 수 없어** ask_user를 MCP로 만들려던 안이 폐기됐다(펜스 블록 후처리로 우회). 브라우저 조작은 다단계 상호작용이라 펜스 우회가 불가능하다.

가설(구현 시 검증): CLI 하네스는 턴마다 `claude -p`를 새로 spawn하고 MCP 브리지도 그때 뜬다 → **브리지 spawn 시 env로 채널 id를 주입**하면 그 턴의 도구 호출이 채널 정체성을 갖는다(`ENGRAM_INSTANCE_ID` 주입 선례와 동일 결). 자체 하네스(API 두뇌)는 `CompleteOpts` 클로저 주입으로 이미 해결된 패턴.
**이 가설이 깨지면 즉시 보고하고 대안을 논의할 것 — 억지로 우회하지 마라.**

## 안전 모델(사용자 확정)
- `자동 확인` 3단계: **매번 묻기 / 내 컴퓨터에서만(기본) / 항상 자동**. 기본값에서 localhost는 자동, 외부 사이트는 매 조작 확인.
- **로그인·결제 정보 입력은 어떤 설정에서도 금지**(하드 규칙 — 설정으로 못 푼다).
- 조작 중인 요소를 화면에 표시(테두리+라벨) + 행동 로그를 남긴다(무엇을 했는지 사후 추적 가능).
- 허용 사이트 목록 관리.

## 검증

- 순수 레이아웃 함수 단위 테스트(분할·닫기·크기·직렬화 왕복).
- 렌더러 통합: 탭 전환·주소 이동·분할 후 두 칸 동시 렌더.
- **실기(Electron) 확인 필수**: webview 실제 로드·뒤로가기 동작·파티션 분리(앱 쿠키 미노출)·종료 후 pty 고아 0.
- AI 조작 단계: 채널 바인딩 실증(두 채널 동시 열고 각자 자기 칸만 조작) · 확인 단계별 차단 동작 · 로그인/결제 필드 입력 거부.
